# Name both contributions, claim neither too much

**Recommended title: "Revisiting the Security of Code from Lower-Cost LLMs and Proposing a Framework That Combines CWE Knowledge with Business Rules"** (19 words). It fits the paper better than any of candidates A–D for three reasons. It names the two contributions in the order the paper delivers them: a measured re-run first, then a design that has not been built. It uses two verbs, "Revisiting" and "Proposing", so no reviewer can mistake the framework for something already implemented and evaluated. And it keeps the one pairing that no existing title uses, "CWE knowledge" with "business rules", while avoiding the most crowded phrase in the field ("Secure Code Generation") and avoiding a near-copy of Kharma et al.'s title. The search found **no existing title that combines CWE with business rules or business logic for code generation** ([arXiv](https://arxiv.org/abs/2502.01853); [IEEE Xplore](https://ieeexplore.ieee.org/document/11197590/)). The real risk is in the content, not the wording. Kharma's own group has already published a 5-model × 4-language follow-up, SecureCoder (IEEE TSE 2025) already pairs CWE retrieval with a "business logic" step, and two 2026 papers already use security tests or access-control specifications before generation. All of them must be cited and set apart in the introduction. Candidate D overclaims, B nearly duplicates the base paper, and A and C put the unbuilt framework in the lead position, which makes them read as method papers that report no method results.

## Two verbs carry the honesty the authors want

The paper has two parts of very different maturity. One is 800 generations with measured outcomes. The other is a design with no implementation. A title that gives both parts the same grammatical weight, or leads with the design, invites the reviewer comment "where is the evaluation of the framework?" In this field, "A Framework for X" by itself normally names a working system, as in SCodeGen and AutoSafeCoder ([SoK refs](https://arxiv.org/pdf/2606.25195)). "Towards" does not reliably signal "not yet built" either: SecCoder (EMNLP 2024) and a USENIX Security 2025 SoK both use it for complete work ([SoK refs](https://arxiv.org/pdf/2606.25195)). The plainest honest marker is a verb or qualifier that cannot be read as a result, such as "Proposing" or "A Proposed Framework".

"Revisiting" is the matching low-risk word for the empirical half. Under the ACM SIGSOFT Empirical Standards, this study is a partial, external, conceptual replication. It reuses Kharma et al.'s research questions but changes the models, prompt, temperature and scanners ([SIGSOFT](https://www2.sigsoft.org/EmpiricalStandards/docs/standards?standard=Replication)). Used without a qualifier, "Replication" in a title invites the objection "why not an exact repeat?" "Revisiting" signals the link to prior work without promising exactness. The SIGSOFT label belongs in the abstract, along with the list of deviations. The Standards also list "rejecting a study because it replicates existing work" as an invalid criticism, which the authors can rely on ([SIGSOFT](https://www2.sigsoft.org/EmpiricalStandards/)).

### Word-by-word justification of the top pick

| Word(s) | Why this word | Rejected alternatives |
|---|---|---|
| **Revisiting** | Accurate for a partial re-run with changed setup. Plain. Signals a follow-up to a named study. | "Replication" (implies an exact repeat unless qualified), "Updated measurement" (rejected by authors), "Benchmark" (no new benchmark is introduced) |
| **the Security of Code** | Names what was measured (scanner findings, compile outcomes, test coverage) without repeating Kharma's "Security and Quality in LLM-Generated Code" word for word. | "Security and Quality of LLM-Generated Code" (near-verbatim base title) |
| **from Lower-Cost LLMs** | This is what makes the study new: Claude Haiku 5.5, GPT-6 Luna, Gemini 3.8 Flash, Mistral Large 4 and Qwen3.8 Flash. No code-security title found frames its models by cost. "Lower-" is relative to the original flagship models, so it is defensible. | "Recent" (dates quickly and says little), "cost-efficient" (states a conclusion), "budget" (informal) |
| **and Proposing** | Marks the second contribution as a design. It is parallel with "Revisiting", so the title reads as one plain sentence. | "Towards" (ambiguous), "A Framework for" alone (reads as a built system) |
| **a Framework** | The standard noun for a multi-step design: requirements, tests, targeted repair, re-checks. The verb "Proposing" removes the risk that it reads as built. | "Approach" (vaguer), "System"/"Tool" (implies an artifact) |
| **That Combines … with** | The new idea is the combination itself. "Combines X with Y" puts the weight on the pairing. | "Using" (suggests a prompting trick), "Integrating" (heavier, says the same thing) |
| **CWE Knowledge** | The framework draws on the CWE catalogue, and reviewers know and search for CWE. CWE catalogues *weaknesses*, so "vulnerability knowledge" is technically looser. | "Vulnerability knowledge", "security knowledge" (vaguer), "CWE-guided" (suggests prompting only), "weakness-aware" (jargon) |
| **Business Rules** | MITRE itself defines business-logic issues as ones that need "business rules" to classify ([CWE-840](https://cwe.mitre.org/data/definitions/840.html)). The term names exactly what developers confirm: ownership, role permissions, workflow order. | "Business logic" (see below), "authorization" (misses workflow order, CWE-841), "application logic" (no anchor in any taxonomy) |

"Business logic" lost to "business rules" for three reasons. MITRE's CWE-840 "Business Logic Errors" is a category whose mapping use is "PROHIBITED". It does not contain the role-check weaknesses CWE-862 and CWE-863, which sit under OWASP's Broken Access Control instead ([CWE-840](https://cwe.mitre.org/data/definitions/840.html); [OWASP A01](https://top10.owasp.org/2021/A01_2021-Broken_Access_Control)). It also already means something different in the closest prior work: SecureCoder uses "business logic" to mean the code's functional intent ([IEEE Xplore](https://ieeexplore.ieee.org/document/11197590/)). "Business rules" describes the input the framework takes, carries no taxonomy baggage, and does not overclaim.

The title leaves out the security tests, the targeted repair, the re-checks across feature edits and the code-location binding. That is deliberate. Each extra noun adds about four words, and the title is already above the 10–15-word guideline ([GMU IEEE guide](https://infoguides.gmu.edu/ieee_style/write)). The abstract's first two sentences should carry these mechanisms. If the venue allows a longer title, alternative 3 below makes them explicit. The title also drops "quality". The measured quality signal is mostly the compile rate (75.5%). Adding "and Quality" would bring back the near-copy of Kharma's title, so add it only if the quality analysis is a full section in its own right.

## Candidates A–D each carry one avoidable flaw

**(A) "Combining CWE Knowledge and Business Rules for Secure LLM Code Generation: A Study of Recent Models and a Proposed Framework."** This is the strongest of the four. It has the distinctive pairing up front, and "Proposed Framework" is honest. Its flaw is the order. The main title states a method ("Combining … for Secure LLM Code Generation") that the paper never runs, and the measured study is pushed into the subtitle as "A Study of Recent Models". That phrase does not say it is a re-run, and "recent" will look dated within a year. At 21 words it is also long. **Verdict: second-best. Fix it by swapping the halves, which gives the top pick.**

**(B) "Revisiting the Security and Quality of LLM-Generated Code: A Study of Recent Models and a Framework for Business-Logic-Aware Secure Generation."** It signals the replication most strongly, but "Security and Quality of LLM-Generated Code" is nearly Kharma's exact title, and "Revisited … Security of LLM-Generated Code" already exists as WildCode Revisited ([arXiv](https://arxiv.org/abs/2502.01853); [arXiv](https://arxiv.org/pdf/2512.04259)). It drops CWE entirely. "Business-Logic-Aware" is a hyphenated coinage that reads as jargon. And "a Framework for" without "Proposed" reads as a built system. **Verdict: weakest on distinctiveness.**

**(C) "Secure Code Generation with LLMs Using CWE Knowledge and Business Rules: Evaluating Recent Models and Proposing a Framework."** It opens with the most crowded stem in the field: more than 15 titles found contain "Secure Code Generation" ([SCGAgent](https://arxiv.org/abs/2506.07313); [RealSec-bench](https://arxiv.org/abs/2601.22706); [SoK](https://arxiv.org/html/2606.25195v1)). Its main title also asserts a working method ("…Using CWE Knowledge and Business Rules") that the paper has not built. The subtitle's verb pair "Evaluating … Proposing" is good and is kept in the top pick. **Verdict: a good subtitle let down by its main title.**

**(D, original) "Generating Secure and High-Quality Code with LLMs by Combining CWE Vulnerability Knowledge and Business Logic Understanding."** No near-duplicate exists, but it is the riskiest on overclaiming. "Generating Secure and High-Quality Code … by Combining" claims an outcome the paper does not show. The data shows only 75.5% of outputs compiling, and nothing has been generated *with* the framework. "Vulnerability knowledge" is looser than CWE's own term, "weakness". "Business Logic Understanding" implies the model understands, which is unmeasurable, and it overlaps conceptually with SecureCoder ([IEEE Xplore](https://ieeexplore.ieee.org/document/11197590/)). It also gives no sign that a measurement study exists. **Verdict: retire it. It describes a future paper, not this one.**

The most dangerous overlap is the Kharma group's 2026 prompting-methods paper. A reviewer who knows it will see "five LLMs, four languages, CWE-aware" and ask what is new. The answer has to be the lower-cost model set, the finding that the approved tests cover only 16.2% and check no security property, and the business-rule half of the framework. That last point is also why "Business Rules" must stay in the title.

Some uncertainty remains. The duplicate search used about 15 web queries and did not query dblp, Google Scholar, ACM DL or IEEE Xplore directly, so titles that appear only at a venue may be missing. Several arXiv titles were seen only in search snippets. Before submission, run exact-phrase searches for "CWE Knowledge" + "Business Rules" and for the final title on Google Scholar and dblp.

## Conclusion

The best title here works by subtraction. It drops the field's most crowded phrase, drops the base paper's exact wording, drops any verb that claims results, and keeps only the words that set this paper apart: "lower-cost", "CWE knowledge" and "business rules". The authors still have to define "lower-cost" with a stated price criterion, because a cost word in a title invites a request for a number. They also need to state the SIGSOFT replication type in the abstract, so that "Revisiting" is backed by a formal label.

The title can only promise a combination. The paper has to show why that combination is needed: scanners flagged 15.9% of compiling outputs, mostly in C, and the approved tests cover only 16.2% and check no security property. These results show that neither tool can confirm a security property. They do not show that business-rule flaws are present, because those were not measured. The business-rule half of the framework is the paper's main claim to novelty, so the most valuable addition before submission would be even a small manual check of ownership, role and workflow defects in the 800 generations. Without one, the title's "business rules" is supported only by argument, not by data.
