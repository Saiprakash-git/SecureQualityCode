\begin{abstract}
Large language models are increasingly used to generate production code, yet
large-scale measurement studies show this convenience carries a persistent
security cost: a multi-language, multi-model analysis of five widely used
LLMs found recurring, language-specific weaknesses such as improper
cryptographic implementation, hardcoded credentials, and memory-safety
violations, with models often ignoring secure language features already
available to them. Subsequent CWE-guided mitigation frameworks reduce such
weaknesses by retrieving relevant vulnerability knowledge during generation,
but recent benchmarks reveal a deeper problem: even when models can
correctly name the right security principle, they frequently fail to apply
it at the correct location in the code, and agents that pass functional
tests remain insecure on the majority of tasks. Security-aware prompting and
iterative refinement do not reliably close this gap, and in several reported
cases security-focused prompting reduces functional correctness, while
deleted or weakened defenses go undetected by static analyzers across
successive code changes. Moreover, existing mitigation approaches operate on
the technical content of a task alone, remaining largely agnostic to the
business logic and access-control expectations, such as ownership,
authorization, and workflow invariants, that govern real-world software but
are rarely stated explicitly in a prompt. This project proposes a
verification-driven framework that synthesizes an explicit, traceable
security and business-logic contract for a given development task from CWE
knowledge, language-specific secure-coding idioms, and an inferred or
developer-supplied business-context profile; generates code guided by this
contract; and verifies each requirement with an executable check, including
generated multi-identity authorization tests that target access-control
flaws invisible to static scanners. A bounded, functionality-preserving
repair step corrects verified failures without unbounded re-prompting or
degrading correctness, and contract tests persist as a regression guard
across subsequent feature changes. The framework is evaluated against
raw-prompting, generic security-prompting, and CWE-only baselines on
functional correctness, security-test pass rate, contract-requirement
coverage, and the survival of earlier security guarantees as new features
are added, with the aim of making LLM-generated code measurably closer to
production-ready while reducing the manual verification burden on
developers.
\end{abstract}

\section{Introduction}

The adoption of large language models (LLMs) for automated code generation
has fundamentally reshaped software development practice, with developers
increasingly relying on AI assistance not only for boilerplate code but for
complete features, and in many cases entire applications generated through
conversational, ``vibe-coding'' workflows. This shift promises substantial
productivity gains, but it also changes where the cost of software defects
falls: instead of a developer writing and reviewing their own logic, a
developer must now review logic they did not write, often faster than they
can meaningfully verify it. As LLM usage and inference cost continue to
scale, the manual effort required to catch an AI assistant's mistakes,
security flaws chief among them, becomes the binding constraint on how much
of the development lifecycle can safely be delegated to AI. Reducing that
verification burden, not merely reducing raw vulnerability counts in
isolation, is therefore the practical problem this work addresses.

Empirical evidence shows the problem is severe and is not improving
proportionally with model capability. A multi-language, multi-model
measurement study of five widely used LLMs found recurring,
language-specific security weaknesses, including improper cryptographic
implementation, hardcoded credentials, and memory-safety violations, with
models frequently failing to use secure language features already available
to them \cite{kharma2026}. More recent agent-level benchmarks sharpen the
picture further: across thirteen agent-model combinations evaluated on
real-world vulnerability-remediation tasks, 90.5\% of tasks were solved
functionally but only 33.0\% securely \cite{agentleague2026}. On a separate
benchmark isolating agent behavior on historical vulnerability fixes, the
best-performing combination was correct and secure on just 10.5\% of tasks,
meaning 82.8\% of its functionally correct solutions remained insecure
\cite{susvibes2026}. Critically, naive mitigations do not close this gap and
can actively worsen it: explicitly telling an agent which CWE to guard
against reduced functional correctness without improving overall security
\cite{susvibes2026}, and a systematic study across multiple secure-coding
interventions found that models consistently \emph{know} the relevant
security principle, scoring well above chance on direct knowledge probes,
yet fail to apply it at the correct location in generated code, a
phenomenon the authors term the ``knowledge--actuation gap'' \cite{sok2026}.

A second, distinct line of work has sought to close this gap by grounding
generation in structured vulnerability knowledge, most commonly the Common
Weakness Enumeration (CWE) taxonomy, retrieving task-relevant CWE entries
and steering generation toward documented mitigations
\cite{securecoder2026}. Such CWE-guided approaches report meaningful
reductions in vulnerability rates, but share two limitations relevant to
this work. First, the guidance they retrieve is selected from the technical
surface of the task alone, the code pattern being requested, with no
representation of the business logic governing the system: who is
authorized to perform an action, what ownership or workflow invariants must
hold, what data is sensitive. Vulnerabilities in this class, such as broken
object-level authorization, missing ownership checks, and workflow-rule
violations, are defined by the absence of logic rather than the presence of
a bad pattern, and are consequently invisible to CWE-pattern retrieval and
to the static analyzers typically used to evaluate these methods. Second,
existing evidence indicates that whatever security gains these methods
achieve at the level of a single, isolated generation can erode across a
realistic development sequence: security-aware prompting shows limited
transfer from function-level to repository-level evaluation
\cite{secrepobench2026}, and iterative, multi-turn refinement has been shown
to degrade the security of previously generated code rather than improve
it, with static analyzers failing to detect the regression
\cite{scaffold2026}.

This project addresses these three compounding gaps, the
knowledge--actuation gap, the absence of business-logic-aware verification,
and the degradation of security guarantees across iterative development,
with a single framework. Rather than steering generation with retrieved CWE
text alone, the proposed framework synthesizes an explicit,
machine-checkable \emph{contract} for each development task, combining
retrieved CWE mitigations, language-specific secure-coding idioms, and a
structured business-context profile, covering roles, assets, trust
boundaries, and invariants, either supplied by the developer or inferred
from the task and existing codebase. Each contract requirement carries its
own verification method, including, where static analysis is structurally
blind, generated multi-identity behavioral tests that directly probe for
missing authorization and workflow-invariant violations. Code is generated
against this contract, verified in a sandboxed environment against
functional tests, contract tests, and static scanners, and, when
verification fails, repaired under a bounded, functionality-preserving
procedure that is explicitly forbidden from altering code tied to
already-satisfied requirements, directly targeting the
correctness-regression trade-off observed in prior security-aware
prompting. Finally, contract tests generated for one feature persist as a
regression suite that is re-run before every subsequent feature is
generated, directly targeting the cross-iteration degradation problem that
static, single-shot evaluation cannot detect.

The contributions of this work are:
\begin{itemize}
\item A structured, traceable contract-synthesis method that unifies CWE
vulnerability knowledge with an explicit business-context profile, where
every requirement carries an executable verification method rather than
being left as unverified guidance text.
\item A behavioral-oracle generation technique that targets business-logic
and access-control vulnerabilities, such as broken object-level
authorization, that are invisible to the static analyzers used in prior
CWE-guided evaluation.
\item A bounded, functionality-preserving repair procedure and persistent
regression-testing mechanism, together targeting the
security--functionality trade-off and the cross-iteration security
degradation documented in recent agent-security literature.
\item An evaluation methodology, contract-requirement coverage, security-test
pass rate alongside functional correctness, and defense survival across a
sequence of added features, that goes beyond the single-shot, function-level
metrics used in most prior CWE-guided work.
\end{itemize}

related work on secure code generation, CWE-guided methods, and agent

research questions this work targets. Section~IV presents the proposed
framework in detail. Section~V describes the experimental setup. Section~VI
reports results and analysis. Section~VII discusses threats to validity, and
Section~VIII concludes with future work.

\section{Related Work}

\subsection{Measurement Studies of LLM Code Security}

Large-scale measurement studies establish that insecure code generation is a
persistent, cross-model property rather than an artifact of any single
system. Kharma~\textit{et al.} \cite{kharma2026} evaluate five widely used
LLMs across four programming languages on a manually vetted 200-task
dataset, finding recurring, language-specific weaknesses, including
cryptographic misuse, hardcoded credentials, and memory-safety violations,
and show that security effectiveness does not track model size or recency.
Industry telemetry corroborates this at production scale: an analysis of
enterprise repositories reports that AI-assisted development increased
commit frequency several-fold while security findings grew roughly
tenfold over a comparable period, with the flaw mix shifting toward
architectural and access-control issues rather than syntax errors
\cite{csa2026}. This work treats \cite{kharma2026} as its base measurement
study and extends it along the axis these measurement studies do not cover:
why security guidance fails to translate into secure code, and how to make
that translation verifiable.

\subsection{Input- and Context-Steering Methods}

A family of methods steers generation by retrieving relevant CWE knowledge
at inference time. SecureCoder \cite{securecoder2026} maps a task to
CWE-aligned security knowledge through multi-label classification and
supplies the resulting guidance as generation constraints. MA-CoT
\cite{macot2026} embeds task-specific CWE mitigation snippets and
language-aware safeguards directly into a chain-of-thought prompt. BRACE
\cite{brace2026} uses an auxiliary LLM call to identify task-relevant CWE
risks, validates them against the official CWE catalog, and supplies
canonical mitigation guidance to the target model. These methods share a
common limitation directly relevant to this work: the CWE guidance they
retrieve is selected from the technical surface of the task description
alone. None represents business logic, such as ownership, authorization
scope, or workflow invariants, and consequently none can guide generation
toward defenses, like object-level authorization checks, whose omission is
not visible in the task's technical surface at all.

\subsection{Training, Alignment, and Constrained Decoding}

A second family trains or constrains the model itself. SRCode
\cite{srcode2026} applies token-level reinforcement-learning rewards,
identifying secure and insecure tokens via a teacher model, and reports
consistent gains on CWEval and CodeLMSec; the authors also report that
vanilla PPO without this shaping reduces functional security performance,
illustrating that naive reward design can be counterproductive. Constrained
decoding approaches \cite{decoding2026} instead restrict the token
distribution at generation time to exclude known-insecure patterns. These
approaches require either a capable teacher model and substantial training
infrastructure, or precise grammars per vulnerability class, both of which
are outside the scope of a framework intended to work with arbitrary,
off-the-shelf LLMs and IDE coding agents. This work treats model training as
a complementary future direction, discussed in Section~VIII, rather than a
precondition for the proposed framework.

\subsection{Post-Generation Feedback and Repair}

A third family generates, checks, and iteratively revises code.
SCAFFOLD-CEGIS \cite{scaffold2026} is the most directly relevant: the
authors show empirically that unconstrained, LLM-driven iterative
refinement exhibits an \emph{iterative refinement paradox}, where security
degrades across successive refinement rounds due to specification drift,
and that naively adding static-analysis gating between iterations does not
suppress this degradation and can increase it. Their proposed mitigation
combines semantic security anchors, invariant checks, and a bounded diff
budget to constrain revision. This finding directly motivates the bounded,
functionality-preserving repair procedure in Section~IV: rather than
permitting unconstrained re-prompting, repair in this work is explicitly
forbidden from altering code already tied to a satisfied requirement, and
is capped at a fixed number of rounds.

\subsection{Benchmarks for Agentic and Repository-Level Secure Code Generation}

Recent benchmarks evaluate coding agents, not just raw model completions,
and consistently report a large gap between functional and secure success.
Across thirteen agent-model combinations on real-world vulnerability tasks,
90.5\% of tasks were solved functionally but only 33.0\% securely, and
explicitly naming the target CWE to the agent did not improve security
while reducing functional correctness \cite{agentleague2026}. LSCBench
\cite{lscbench2026} evaluates three granularities of task scope and finds
that 56.0\% of its tasks were secured by no evaluated model, and that
additional agent turns did not improve security outcomes. SecRepoBench
\cite{secrepobench2026} shows that security-aware prompting, effective at
the function level, contributes almost no measurable gain at the
repository level, and that a repair agent built for this setting fixed none
of 43 insecure repository-scale completions. SecureVibeBench
\cite{securevibebench2026} and EvoCode-Bench \cite{evocode2026} extend
evaluation to multi-file and multi-turn settings respectively; the latter
finds that regression, correct behavior breaking after a later edit, is a
leading failure mode for top-tier agents, but does not evaluate regression
of \emph{security} properties specifically. No benchmark surveyed couples
regression analysis with a security oracle across a sequence of
feature-adding tasks, which is the evaluation gap Section~V addresses.

\subsection{Specification- and Context-Driven Security}

The work closest in spirit to this proposal is the Specification-Driven
Development Benchmark \cite{specdriven2026}, which introduces a Multilayer
Specification Security Model linking system entities, threats, risks, and
controls, and a Security Knowledge Transition Method that converts business
and technical specifications into a security-enriched generation contract.
Against a hidden 221-test API suite, the authors report failures falling
from 50 under a no-security baseline to 42 under ASVS conditioning and 36
under their model, with the largest gains in business-logic and
admin-safety categories, directly corroborating that explicit business
context improves generation outcomes beyond CWE guidance alone. This work
differs in three respects. First, \cite{specdriven2026} evaluates
generation as a single conditioned pass against a fixed hidden suite; this
work instead generates an executable, task-specific oracle, including
multi-identity authorization tests, as part of the contract itself, rather
than relying solely on a separate held-out test suite. Second,
\cite{specdriven2026} does not report a repair mechanism; failing
generations are not revised under an explicit functionality-preserving
constraint. Third, \cite{specdriven2026} evaluates single-pass generation
only; it does not address the degradation of security guarantees across a
sequence of feature additions, which Section~IV's regression guard and
Section~V's defense-survival metric are designed to measure.

\begin{abstract}
Large language models now write a growing share of production code, yet
measurement studies show that the code they produce repeatedly carries
language-specific weaknesses such as cryptographic misuse, hardcoded
credentials and memory-safety errors. Recent evidence sharpens the problem:
models answer secure-coding questions almost perfectly but fail to apply the
same knowledge in generated code, static analyzers overstate the security of
that code several-fold, authorization and business-logic flaws are invisible
to pattern-based tools, and security degrades as code is edited over
successive turns. Supplying more vulnerability knowledge in the prompt
therefore does little. This paper argues that the missing element is the
location of enforcement. We present ContractGuard, a framework that compiles
CWE-derived mitigations and developer-confirmed business rules, such as
ownership, role permissions and workflow invariants, into typed obligations,
and binds each obligation to a named enforcement slot in a code skeleton
before any implementation is written. The binding then serves three
purposes: every generated security test is trusted only after it fails on a
deliberately weakened version of its own slot, repair of a failing
obligation is confined to that slot, and validated tests are carried forward
as a regression ledger so that later features cannot silently remove earlier
defenses. Each obligation ends as passed, failed, or explicitly waived for
human review, which narrows what a developer must inspect. We define
measurable notions of secure and production-ready code, describe an
evaluation against strong agentic and specification-based baselines, and
report an updated measurement of five current cost-efficient models across
four languages.
\end{abstract}

\section{Introduction}
%==========================================================================

Large language models (LLMs) have moved from completing lines of code to
writing whole features and, through conversational ``vibe coding''
workflows, whole applications. This changes where the cost of a defect
falls. A developer no longer reviews logic they wrote; they review logic an
assistant wrote, often faster than they can verify it. Controlled studies
suggest the cost is real: participants with an AI assistant wrote less
secure code while being more confident it was secure \cite{perry2023}, and
experienced open-source developers in a randomized trial were 19\% slower
with AI assistance while believing they were 20\% faster, spending part of
their time reviewing and cleaning AI output \cite{metr2025}. As generation
becomes cheaper and review does not, the effort needed to establish that
generated code is safe becomes the limiting factor. Reducing that effort,
rather than only reducing vulnerability counts, is the practical problem this
work addresses.

The underlying weakness is well documented. Kharma \textit{et al.} measured
five LLM families on 200 tasks in four languages and found recurring,
language-specific weaknesses, with cryptographic misuse such as RSA without
OAEP (CWE-780), hardcoded passwords (CWE-259) and improper certificate
validation (CWE-295) prominent in Java and Python, and buffer errors such as
CWE-120 in C \cite{kharma2026}. Agent benchmarks show the same pattern at
larger scale. On real-world feature tasks, the best agent configuration in
SusVibes passed functional tests on 61.0\% of tasks but was also secure on
only 10.5\% \cite{susvibes2026}, and on exploit-tested backend tasks roughly
half of functionally correct programs were exploitable \cite{baxbench2025}.

Three findings explain why existing mitigations struggle. First, knowledge
is not the bottleneck: across eighteen model and benchmark slices, models
answered secure-coding questions with 93.7--96.5\% accuracy, yet the gap
between knowledge and secure generation was 47.9 points on CWEval and 72.9
points on BaxBench \cite{sok2026}. Methods that retrieve more CWE guidance
into the prompt \cite{securecoder2026,macot2026,csdd2026} therefore address
the part of the problem that is already largely solved. Second, the
checkers used to measure progress are unreliable: CodeQL rated 64.8--98.5\%
of outputs from secure-generation methods as secure while only
3.0--13.3\% were both secure and functional \cite{tessa2026}, and
static analyzers cannot see a missing ownership check at all, because there
is no source-to-sink pattern for ``this user must not see that order.''
Third, security is not stable over time: correct-and-secure rates fall by
20--27\% when tasks are spread over multiple turns \cite{mtsec2025}, and
feature-adding steps were the most likely to degrade security in long
refinement chains \cite{scaffold2026}.

Business logic sits at the intersection of these problems. The closest work,
a specification-driven pipeline that derives a multilayer security model
from business and technical specifications, reduced business-logic test
failures from 17 to 9 on a booking API, but never executed its own
verification layer \cite{specdriven2026}; a CWE-tagged constitution approach
explicitly leaves business-logic flaws out of scope \cite{csdd2026}. Repair
loops add their own failure mode: methods that iterate until a checker is
satisfied often do so by deleting or breaking functionality
\cite{dai2025,sok2026}.

This paper takes the position that the missing element is the
\emph{location} of enforcement. A requirement such as ``only the owner may
cancel a booking'' is satisfied only if a check exists at one specific place
on the request path, before the state change. We present \sys{}, which makes
that place a first-class object. \sys{} compiles CWE-derived mitigations and
developer-confirmed business rules into typed \emph{obligations}, and binds
each obligation to a named \emph{slot} in a code skeleton before
implementation begins, following the spirit of Design by Contract
\cite{meyer1992}. The binding is then used three ways. A generated security
oracle is trusted only if it fails when its own slot is replaced by a
permissive mutant, giving every test built-in evidence that it can detect
the flaw it targets. Repair of a failing obligation may edit only the
corresponding slot. Validated oracles are committed with the code as a
ledger and must remain green as later features are added. Each obligation
ends as PASS, FAIL, or WAIVED, so a reviewer reads a short list of what was
not proven rather than every generated line.

The contributions of this work are:
\begin{itemize}
\item \textbf{Slot-bound security contracts.} A typed obligation schema that
unifies CWE-derived and business-context requirements, each with a source,
severity, slot and verifier kind, together with a skeleton-first binder and a
static check that every route reaches its bound guards.
\item \textbf{Mutation-validated invariant oracles.} Deterministic generation
of multi-identity authorization and workflow oracles from a confirmed access
matrix, with slot-targeted mutation that makes oracle adequacy a reported
quantity and separates ``waived'' from ``passed.''
\item \textbf{Slot-scoped repair and a defense-survival protocol.} A repair
step that cannot modify code outside the failing slot, and an evaluation
protocol that measures how many validated defenses survive each added
feature.
\item \textbf{An updated measurement and a controlled evaluation design.} A
replication of the base study on five current cost-efficient models, and an
evaluation plan with joint functional and security metrics against strong
agentic, specification-based and repair baselines.
\end{itemize}

Section~II reviews related work. Section~III defines the problem, threat
model and metrics. Section~IV presents \sys{}. Section~V describes the
experimental setup, Section~VI reports results, Section~VII discusses threats
to validity, and Section~VIII concludes.

\section{Related Work}
%==========================================================================

\subsection{Measuring the Security of Generated Code}

Kharma \textit{et al.} \cite{kharma2026} provide the measurement baseline
this work extends: a curated 200-task dataset in seven categories, four
languages and five model families, evaluated for compilation, unit-test
correctness, and quality and security with SonarQube and CodeQL. Perry
\textit{et al.} \cite{perry2023} showed in a user study that assistance can
lower security while raising confidence. Later work moved to executable
evaluation. BaxBench pairs 392 backend tasks with expert exploits and found
the best correct-and-secure rates around 35--37\% \cite{baxbench2025};
CWEval provides function-level tasks with executable functional and security
tests \cite{cweval2025}; SusVibes and an independent re-run by Endor Labs
evaluate agents on repository-level feature tasks, where pooled across
thirteen agent and model pairs 90.5\% of tasks were solved functionally but
only 33.0\% securely \cite{susvibes2026,endor2026}.

These studies also expose evaluation pitfalls that shape our design. Static
verdicts overstate security by 7.4--21.6 times relative to combined static
and functional checks \cite{tessa2026}, and on 1,080 human-labelled samples
Semgrep and CodeQL agreed with human judgement on only 65\% and 61\% of
samples \cite{sastlabels2026}. Agents also find shortcuts: in one SusVibes
run, an agent recovered known fixes from git history in 163 of 200 tasks
\cite{endor2026}. We therefore use executable oracles as the primary
security measure, treat static findings as secondary, and isolate the
sandbox from network and version history.

\subsection{Steering Generation with Vulnerability Knowledge}

A large family of methods adds security knowledge at inference time.
SecureCoder maps a task to CWE descriptions and derives guidelines
\cite{securecoder2026}; MA-CoT retrieves task-specific CWE mitigations into
a chain-of-thought prompt and was evaluated on the base paper's dataset with
static tools and manual review \cite{macot2026}; BRACE uses an LLM to
identify task-relevant CWE risks and validates them against the CWE catalog
\cite{brace2026}; Constitutional Spec-Driven Development (CSDD) encodes
CWE-tagged principles with MUST/SHOULD levels and reports CWE violations
falling from 11 to 3 on a single application, with targeted principles
outperforming the full set \cite{csdd2026}. The systematization by Patir
\textit{et al.} explains why such gains are bounded: models already know the
principles, and the gap lies in applying them at the right place
\cite{sok2026}. Among its recommended directions are sink-grounded guidance
and localized, function-preserving repair, neither of which it found
implemented. CSDD comes closest by producing a file-and-line traceability
matrix, but the matrix is produced with or after implementation and, in the
authors' words, measures documented traceability rather than security
effectiveness \cite{csdd2026}. \sys{} instead binds obligations before
implementation and ties each binding to an executable, validated oracle.

\subsection{Execution Feedback, Agents and Repair}

Executing code is a strong baseline. In the same systematization, an agent
scaffold with no security component raised secure-pass@1 on CWEval from 60.5
to 91.6 for one model, but only from 34.2 to 41.8 on the multi-endpoint
BaxBench tasks \cite{sok2026}. SCGAgent generates unit tests, predicts
likely CWEs and applies guidelines with re-testing; it improved one model
but degraded others because self-generated tests were unreliable, and its
CWE prediction recall was 0.448 \cite{scgagent2025}. Supplying security
tests to the model as an upfront specification improved results by 19.3
points on 31 Python tasks, but the tests were benchmark-provided, did not
cover authorization, and repair required replacing the whole module
\cite{testsasspec2026}. A static-analysis feedback loop using Bandit, Pylint
and CodeQL lowered the insecure rate from about 43--45\% to 13.41\% while
improving correctness \cite{blyth2025}. Repair loops also over-correct: an
independent re-evaluation found that 10--30\% of tasks solved by base models
broke after applying secure-generation methods, with one method resolving
most failures by deleting the vulnerable code \cite{dai2025}. LLM-written
exploits are unreliable unless validated by execution: 44--71.5\% of
proof-of-concept exploits that agents counted as successful were invalid
\cite{pocgym2026}, whereas requiring an exploit to fail on a secure solution
and succeed on a weakened one yielded 96.77\% expert-rated soundness
\cite{autobax2025}. \sys{} adopts this contrastive idea but obtains the
weakened variant by mutating the bound slot, which does not require a
reference solution.

\subsection{Business Logic, Specifications and Authorization}

Grynets \textit{et al.} \cite{specdriven2026} propose a Multilayer
Specification Security Model covering actors, roles, assets, trust
boundaries and ownership, fed to an agent through GitHub Spec Kit. On a
FastAPI booking API with a hidden 221-test suite, total failures fell from 50
without security requirements to 42 with ASVS conditioning and 36 with their
model, and business-logic failures fell from 17 to 9. The authors list
executing the verification scenarios, mapping requirements to code,
post-generation repair and multi-turn work as future work; these are the
gaps \sys{} targets. LLM threat elicitation remains only moderately
accurate: the same pipeline fully covered 45.45\% of reference threats
\cite{specdriven2026}, and open 8B models peaked at 68.75\% penalized F1 on
STRIDE classification \cite{threatmodel2026}. AutoCedar shows how to make
intent reliable: humans approve must-permit and must-deny boundaries, after
which a solver-guided loop produced verified Cedar policies for all 221
tasks \cite{autocedar2026}. Automated broken object-level authorization
(BOLA) detection with multiple identities exists for deployed APIs
\cite{authprobe2026}, but covers read access on existing services rather than
generated code. \sys{} combines these ideas: the developer confirms an access
matrix, and oracles for both read and write operations are generated from it
deterministically.

\subsection{Security Across Turns}

MT-Sec measured a 20--27\% relative drop in correct-and-secure rate from
single-turn to multi-turn tasks, with a control showing the drop is not
explained by context length, and found that feedback from ground-truth tests
recovered most of the loss \cite{mtsec2025}. SCAFFOLD-CEGIS found that
feature-enhancement steps degraded security in 52.8\% of cases, that adding
static-analysis gating alone increased latent degradation from 12.5\% to
20.8\%, and that semantic anchors with diff budgets reduced degradation to
2.1\% \cite{scaffold2026}. EvoCode-Bench reports functional regression as a
leading failure mode for strong agents but does not score security
\cite{evocode2026}. \sys{} replaces static counts with executable,
validated oracles that persist across turns, and constrains repair by slot
rather than by diff size.

\subsection{Training-Based Methods}

Training approaches fine-tune models on secure and insecure pairs, use
preference optimization, or apply reinforcement learning with security
rewards \cite{srcode2026,secvec2026}, and constrained decoding restricts
generation to avoid known-insecure patterns \cite{codeguardplus2024}. Their
security signals come mostly from static analyzers or teacher models, which
inherit the checker problems above. We treat training as future work and
note that \sys{} produces data, oracle-labelled slot repairs, that could
serve as an executable reward signal.

\section{Problem Formulation}
%==========================================================================

\subsection{Scope and Threat Model}

We target server-side web applications and APIs, where business logic and
access control matter most and where executable oracles can be run against
an HTTP interface. The adversary is any client of the generated service. It
may be unauthenticated or may hold valid credentials for one or more
identities, and it can send arbitrary requests. Its goals are to read or
modify resources owned by another identity (broken object-level
authorization, CWE-639/863), invoke operations its role does not permit
(broken function-level authorization, CWE-862), drive an object through a
forbidden workflow transition (CWE-841), exceed quotas, or reach an
injection or path-traversal sink (for example CWE-89, CWE-78, CWE-22). We
trust the developer who confirms the security profile, the sandbox, and the
verification tools. Prompt injection against the coding agent, compromise
of the model provider, side channels, and infrastructure misconfiguration
are out of scope.

\subsection{Definitions}

A task $t$ consists of a natural-language description and, optionally, an
API specification. A generator produces a program $P$ for $t$.

\textbf{Security context profile.} A profile
$\Pi = (R, A, V, \mathit{own}, M, I)$ lists roles $R$, resource types $A$,
operations (verbs) $V$, an ownership relation $\mathit{own}$ between
identities and resources, an access matrix
$M: R \times A \times V \rightarrow \{\mathit{allow}, \mathit{deny},
\mathit{own\text{-}only}\}$, and a set of invariants $I$ written as
conditional ``if/when \dots{} the system shall \dots'' statements, for
example workflow-order or quota rules.

\textbf{Obligation and contract.} An obligation is a tuple
$o = (\mathit{id}, \mathit{src}, \mathit{ref}, \mathit{sev}, \kappa,
\nu)$, where $\mathit{src} \in \{\Pi, \mathrm{CWE}\}$ records whether it
comes from the profile or from vulnerability knowledge, $\mathit{ref}$
lists CWE or ASVS identifiers, $\mathit{sev} \in \{\mathrm{MUST},
\mathrm{SHOULD}\}$, $\kappa$ is a slot kind (object authorization,
function authorization, state transition, query construction, path
resolution, and so on), and $\nu$ is a verifier kind (multi-identity replay,
workflow-order test, injection test, static rule, or manual). A contract
$C$ is the set of obligations for $t$; $C_{\mathrm{MUST}}$ denotes its
mandatory subset.

\textbf{Skeleton, slots and binding.} A skeleton $S$ is a program with
routes, signatures and named stub functions called \emph{slots}
$s_1, \dots, s_m$. Slots are stubbed \emph{permissively}, for example an
authorization slot returns true. A binding $\beta: C \rightarrow S$ assigns
each obligation to the slot that must enforce it. A binding is
\emph{well-formed} if every obligation in $C_{\mathrm{MUST}}$ is bound and,
for every route that touches a resource governed by $o$, the call graph of
the route reaches $\beta(o)$.

\textbf{Oracle validity.} An oracle $\omega_o$ is an executable test for
$o$, with $\omega_o(P) \in \{\mathit{pass}, \mathit{fail}\}$. Let
$\mu_s(P)$ denote $P$ with slot $s$ replaced by a permissive mutant. We call
$\omega_o$ \emph{valid on $P$} if
\begin{equation}
\omega_o(P) = \mathit{pass} \;\wedge\;
\omega_o(\mu_{\beta(o)}(P)) = \mathit{fail},
\label{eq:validity}
\end{equation}
that is, the oracle accepts the program and kills the mutant of its own
slot. An oracle that passes on $P$ but also passes on the mutant is
\emph{vacuous}: it cannot detect the flaw it is meant to detect.

\textbf{Obligation status.} After verification and bounded repair, each
obligation receives one status. It is PASS if its oracle is valid on $P$,
FAIL if its oracle still fails after the repair budget is exhausted, and
WAIVED if its oracle is vacuous or its verifier kind is manual. WAIVED
obligations are reported for human review and never counted as passed.

\textbf{Admissible repair.} For a failing obligation $o$, a patch $\delta$
is admissible if every changed line lies within the source span of
$\beta(o)$, the binding remains well-formed after the patch, and all
functional tests and all previously passing oracles still pass.

\subsection{Metrics}

Following recent recommendations to report functional and security results
jointly \cite{sok2026,dai2025}, we use the following task-level metrics.
\emph{pass@1} is the fraction of tasks whose solution passes the benchmark's
functional tests. \emph{secure-pass@1} is the fraction whose solution passes
the functional tests and every \emph{held-out} security test; held-out tests
are written independently of \sys{} and are never shown to any system.
\emph{secure@pass} is secure-pass@1 divided by pass@1. A solution is
\emph{production-ready} if it is secure and also clears a quality gate $Q$:
no error-class lint findings or reliability bugs, function complexity and
maintainability within thresholds declared before the experiments, every
dependency present in its registry with no known-vulnerable pinned version,
no committed secrets, and validation on public entry points.
\emph{production-ready@1} is the corresponding fraction. Static findings
are reported separately and never enter secure-pass@1.

At the contract level, \emph{contract coverage} is the fraction of
$C_{\mathrm{MUST}}$ that ends PASS, \emph{oracle adequacy} is the fraction of
oracles that kill their slot mutant, and \emph{waive rate} is the fraction
that ends WAIVED. For a sequence of feature additions $1, \dots, K$ with
ledger $L_{k}$ of oracles validated up to step $k$, \emph{defense survival}
at step $k$ is
\begin{equation}
\mathit{DS}_k = \frac{|\{\, o \in L_{k-1} : \omega_o \text{ valid on } P_k
\,\}|}{|L_{k-1}|}.
\label{eq:ds}
\end{equation}
As a proxy for review effort we report the number of items needing human
attention (WAIVED and FAIL obligations plus unresolved static findings
confirmed by two tools) and the number of lines changed outside bound slots.

\begin{itemize}
\item[\textbf{RQ1}] How secure and how maintainable is code from current
cost-efficient LLMs across four languages, compared with the base study

\item[\textbf{RQ2}] Does \sys{} raise secure-pass@1 and production-ready@1

\item[\textbf{RQ3}] How reliable are the generated oracles, and how much does

\item[\textbf{RQ4}] Do validated defenses survive feature additions better

\item[\textbf{RQ5}] Which mechanisms account for the effect, and at what cost

\item[\textbf{RQ6}] Does the per-obligation evidence report reduce what a

\end{itemize}

\subsection{Profiler}

The profiler asks an LLM to draft a security context profile $\Pi$ from the
task description and any API specification: roles, resource types,
ownership, the access matrix, and invariants in conditional form. The
developer then confirms or edits a short checklist rather than writing the
profile from scratch. This follows evidence that LLM-only threat elicitation
is incomplete \cite{specdriven2026,threatmodel2026} while human-approved
intent boundaries make downstream verification reliable \cite{autocedar2026}.
The profile is stored as validated YAML so that later stages treat it as
data, not prose. To measure the value of confirmation (RQ3) we also run an
LLM-only path.

\subsection{Obligation Compiler}

The compiler deterministically maps profile entries and code features to
obligations. Ownership entries yield object-authorization obligations
(CWE-639/863), role restrictions yield function-authorization obligations
(CWE-862), workflow invariants yield state-transition obligations (CWE-841),
quotas yield rate or limit obligations, and detected sinks yield query,
command and path obligations (for example CWE-89, CWE-78, CWE-22). Per-language
priors come from the weaknesses most frequently observed by the base study,
such as cryptographic and certificate-validation weaknesses in Java and
Python \cite{kharma2026}. We use rules rather than asking an LLM to predict
CWEs, because LLM prediction recall was 0.448 in prior work
\cite{scgagent2025}, and we cap each slot at its three to five relevant
obligations, since targeted principles outperformed the full set in CSDD
\cite{csdd2026}.

\subsection{Skeleton Binder}

Before implementation, an LLM proposes a skeleton: routes, function
signatures and named slots such as
\texttt{authz\_booking\_cancel(user, booking)} or
\texttt{guard\_cancel\_transition(booking, now)}. Slots are stubbed
permissively. The binder assigns every obligation to a slot and checks,
by static analysis of the abstract syntax tree, that every route touching a
governed resource calls its bound slots. This wiring check also catches a
failure seen in practice, where a guard is defined but never connected to
the request path. Binding before implementation gives the generator a
concrete place to put each defense, which is the sink-grounded guidance the
systematization identified as missing \cite{sok2026}.

\subsection{Oracle Forge}

For every cell of the access matrix and every invariant, the forge
instantiates a deterministic oracle template. Authorization templates use
at least two identities: identity B attempts to read, update or delete a
resource owned by identity A, and the oracle checks observable effects only,
namely the status code, whether A's identifier appears in the response, and
whether A's resource changed. Function-level templates call privileged
operations with an unprivileged role. Workflow templates drive an object
into a forbidden state order. Injection and path templates send payloads to
bound sinks. An LLM fills only request bodies and call sequences; pass and
fail decisions are never made by an LLM. Because slots are permissive, every
oracle must fail on the skeleton before generation; an oracle that passes on
the skeleton is discarded. This avoids trusting self-reported exploit
success, which was invalid in 44--71.5\% of cases in prior work
\cite{pocgym2026}.

\subsection{Slot-Filling Generator}

The generator implements the skeleton. Each slot is presented with only its
bound obligations, expressed as a short contract docstring with
preconditions and the expected sink-specific pattern, such as a
parameterized query or an ownership comparison against the authenticated
identity. Oracles are not shown to the generator, which avoids writing code
to the test. The generator can be any LLM or a coding agent; \sys{} only
requires that it preserves slot names and signatures.

\subsection{Verification Gate}

The gate runs in a container without network access or version history and
applies nine checks:
G1~functional tests;
G2~contract oracles;
G3~slot mutation, in which each bound slot is replaced by its permissive
mutant (for example an authorization guard that returns true, a dropped
authentication dependency, a parameterized query rewritten as string
formatting, a removed path canonicalization or a deleted state check) and
the corresponding oracle must flip to fail, per (\ref{eq:validity});
G4~wiring, re-running the call-path check so that a guard cannot be removed
or bypassed;
G5~static analysis with Semgrep and Bandit or CodeQL;
G6~quality with a linter and complexity metrics;
G7~dependency existence in the package registry and known-vulnerability
checks;
G8~secret scanning; and
G9~integrity, in which oracle files are hash-locked so that any skip,
deletion or edit by the generator fails the task.
G3 is the key addition. It turns ``the tests passed'' into ``the tests
passed and are capable of failing,'' reusing the contrastive principle of
AutoBaxBuilder \cite{autobax2025} and the logic of mutation testing
\cite{jia2011} without needing a reference solution.

\subsection{Slot-Scoped Repairer}

When an oracle fails, the repairer maps it to its obligation and slot and
gives the model only three inputs: the body of that slot, the obligation
text, and the failing request and response trace. A patch is rejected if any
changed line falls outside the slot's source span, if it removes a guard or
breaks the wiring check, or if it breaks functional tests or previously
passing oracles. Repair stops after three rounds, consistent with reports
that feedback gains taper after three to four iterations \cite{blyth2025}.
Confining repair by location rather than by diff size distinguishes this
step from diff budgets \cite{scaffold2026} and from whole-module repair
\cite{testsasspec2026}, and it removes the opportunity to ``fix'' a failure
by deleting unrelated functionality \cite{dai2025}.

\subsection{Evidence Report and Contract Ledger}

The evidence report lists every obligation with its status, slot location,
oracle, whether the mutant was killed, and any static or quality findings,
in Markdown and in SARIF so that it appears in pull-request review. A
reviewer needs to read only WAIVED and FAIL entries and changes outside
bound slots. The ledger commits validated oracles and bindings with the
code. When the next feature is requested, the profiler, compiler and binder
run on the change only, and every oracle already in the ledger must remain
valid; defense survival (\ref{eq:ds}) measures how often it does. In agent
workflows the ledger can run as a pre-commit or tool hook.

\begin{algorithm}[t]
\caption{\sys{} for one feature step $k$}
\label{alg:cg}
\begin{algorithmic}[1]
\REQUIRE task $t_k$, program $P_{k-1}$, ledger $L_{k-1}$
\STATE $\Pi \leftarrow$ \textsc{Confirm}(\textsc{DraftProfile}($t_k$))
\STATE $C \leftarrow$ \textsc{Compile}($\Pi$, CWE catalog)
\STATE $(S, \beta) \leftarrow$ \textsc{Bind}($C$, $P_{k-1}$); require well-formed $\beta$
\STATE $\Omega \leftarrow \{\omega_o \leftarrow \textsc{Forge}(o) : o \in C\}$; drop $\omega_o$ with $\omega_o(S) = \mathit{pass}$
\STATE $P \leftarrow$ \textsc{Generate}($S$, $C$)
\FOR{$r = 0$ \TO $3$}
  \STATE $F \leftarrow \{o : \omega_o(P) = \mathit{fail}\} \cup \{o \in L_{k-1} : \omega_o \text{ not valid on } P\}$
  \IF{$F = \emptyset$ \OR $r = 3$}
    \STATE \textbf{break}
  \ENDIF
  \FORALL{$o \in F$}
    \STATE $\delta \leftarrow$ \textsc{Repair}($\beta(o)$, $o$, trace)
    \IF{$\delta$ admissible}
      \STATE $P \leftarrow P \oplus \delta$
    \ENDIF
  \ENDFOR
\ENDFOR
\FORALL{$o \in C$}
  \STATE status$(o) \leftarrow$ PASS if $\omega_o$ valid on $P$ (\ref{eq:validity}); FAIL if $\omega_o(P) = \mathit{fail}$; else WAIVED
\ENDFOR
\STATE $L_k \leftarrow L_{k-1} \cup \{\omega_o : \text{status}(o) = \text{PASS}\}$
\RETURN $P$, report, $L_k$
\end{algorithmic}
\end{algorithm}

\subsection{Worked Example}

For a booking service, the developer confirms one access-matrix row, ``a
member may cancel only their own booking; an administrator may cancel any
booking,'' and one invariant, ``if a booking is not confirmed or its start
time has passed, the system shall reject cancellation.'' The compiler emits
obligation $o_7$ (object authorization, CWE-639/863, MUST, multi-identity
replay) and $o_8$ (state transition, CWE-841, MUST, workflow-order test).
The binder creates \texttt{authz\_booking\_cancel} and
\texttt{guard\_cancel\_transition}, both permissive, and confirms that the
cancel route calls both. The forge produces two oracles: member B attempts to
cancel member A's booking and must receive a denial with A's booking
unchanged, and a cancellation after the start time must be rejected. Both
fail on the skeleton. After generation both pass. The gate then replaces
\texttt{authz\_booking\_cancel} with a function that returns true; if the
$o_7$ oracle does not fail, it is vacuous and $o_7$ is reported WAIVED, not
PASS. If the $o_8$ oracle fails, only \texttt{guard\_cancel\_transition} and
the failing trace are sent to the repairer. When a later feature adds
rescheduling, both oracles remain in the ledger and must stay valid.

\subsection{Implementation}

We implement \sys{} in Python for FastAPI services. Profiles and contracts
use YAML validated with Pydantic; the binder and wiring check use Python's
abstract syntax tree tooling; oracles use pytest with FastAPI's test client;
mutants are produced by rewriting slot bodies; static and quality checks use
Semgrep, Bandit, CodeQL, Ruff and radon; dependency checks use the package
registry and vulnerability databases; and the gate runs in Docker. Model
access goes through a provider-independent client so that hosted models and
a local open-weight coder can be swapped. Oracle templates for multi-identity
authorization require no LLM, which keeps the method affordable.

\subsection{Benchmarks for the Framework (RQ2--RQ6)}

\textbf{BaxBench subset.} Python-framework scenarios from BaxBench
\cite{baxbench2025}, prioritizing scenarios whose expert exploits cover
access-control weaknesses. Exploits serve as held-out security tests.

\textbf{CWEval subset.} Python tasks from CWEval \cite{cweval2025}, which
supply executable functional and security tests at function level, where
bindings attach mostly to sinks rather than to authorization.

\textbf{Custom authorization services.} Ten to fifteen small FastAPI
services, such as bookings, multi-tenant notes, orders with refunds and
document sharing, each with an access matrix, workflow invariants and a
hidden security suite written by a team member who did not write the oracle
templates. Tasks are written after the evaluated models' training cut-offs.

\textbf{Feature sequences.} Each custom service is extended over four to five
feature turns covering expansion, editing and refactoring, following the
taxonomy of MT-Sec \cite{mtsec2025}, with code supplied to the model as
diffs.

\subsection{Models}

For RQ2--RQ6 we use two of the five measurement models and one local
open-weight coding model, so that results cover both hosted and
self-hosted settings and show where the method stops helping weaker models.

\subsection{Baselines}

All baselines use the same model, the same sandbox and the same cap on
model calls and tokens.
B0~direct generation.
B1~a generic security reminder.
B2~MA-CoT-style prompting with retrieved CWE mitigations \cite{macot2026}.
B3~profile-conditioned specification without binding, in the style of
\cite{specdriven2026}, with an ASVS-only variant.
B4~\sys{}'s own validated oracles given upfront as a specification, with
whole-module repair \cite{testsasspec2026}; this isolates the effect of
binding and slot-scoped repair from simply having good tests.
B5~an open-source coding agent that may run functional tests and write its
own tests, the strongest generic baseline \cite{sok2026}.
B6~an SCGAgent-style loop of self-generated tests and CWE guidelines
\cite{scgagent2025}.
B7~anchor and diff-budget repair approximating SCAFFOLD-CEGIS
\cite{scaffold2026}, with budgets declared in advance.
B8~a static-analysis feedback loop \cite{blyth2025}.

\subsection{Metrics and Ablations}

Every table reports pass@1, secure-pass@1 and secure@pass together, plus
production-ready@1, contract coverage, oracle adequacy, waive rate, defense
survival, the review-effort proxy, and cost in tokens, calls and wall-clock
time (Section~III). Ablations remove one mechanism at a time: binding
(contract as a prose checklist), mutation validation (oracles trusted as
generated), slot-scoped repair (whole-file repair), the business profile
(CWE obligations only), the CWE catalog (profile obligations only), and the
ledger. Two further comparisons contrast LLM-generated with deterministic
authorization oracles, and LLM-only with developer-confirmed profiles. The
binding ablation and the comparison with B4 are decisive: if binding adds
nothing over the same validated oracles given upfront, the remaining
contributions are the validated oracles and the defense-survival protocol,
and we will report that outcome as such.

\subsection{Validity Protocol}

The sandbox has no network and no version history, and all tool calls are
logged. Held-out tests never appear in any prompt. Oracle files are
hash-locked. Oracle templates and hidden suites have different authors.
Every configuration runs with at least three seeds; we report bootstrap 95\%
confidence intervals and compare paired outcomes with McNemar's test and
Holm correction. A random 10\% of secure verdicts are audited manually.
Generation failures count as failures. Quality thresholds and repair
budgets are fixed before the main runs.

\section{Threats to Validity}

\textbf{Internal validity.} A framework that writes its own tests risks
grading itself. We separate the two roles: \sys{}'s oracles drive generation
and repair, but every reported security result comes from held-out exploits
or hidden suites written by a different author, and those are never shown to
any system. Oracles may also reject correct code; we measure this false-fail
rate by running every oracle on reference-secure solutions. Results from
agents vary between runs, and published agent results have shifted by several
points on re-runs \cite{endor2026}, so every configuration uses at least three
seeds and paired statistical tests. Contamination and shortcutting are
limited by writing custom tasks after the models' training cut-offs and by
removing network access and version history from the sandbox. The developer
confirmation step is a potential weak point, since people tend to accept
plausible but wrong LLM suggestions; the LLM-only profile ablation measures
how much the result depends on it.

\textbf{Construct validity.} Slot mutation shows that an oracle can detect
the \emph{absence} of a defense, because the permissive mutant removes the
check entirely. It does not show that the check is correct for every input:
an oracle could kill the permissive mutant yet miss a partially wrong guard,
for example one that checks the role but not ownership. Richer mutation
operators, such as partial-guard and off-by-one-state mutants, would tighten
this and are left to future work. For RQ1, static findings from SonarQube and
CodeQL are imperfect measures of security \cite{tessa2026,sastlabels2026};
we report them as finding density, not as a secure rate. The review-effort
measure is a proxy, the number of items a reviewer must inspect, and not
measured human effort; any claim about effort reduction is limited to that
proxy unless a user study is added.

\textbf{External validity.} The dynamic oracle layer targets Python and
FastAPI services, and the custom tasks are small services rather than large
repositories; results may not transfer to other frameworks, to languages
without comparable test tooling, or to repository-scale changes. The
multi-language claim rests on the RQ1 measurement, which uses static tools
only. Method effects can depend on the model: a prior test-and-guideline
loop helped one model and hurt others \cite{scgagent2025}. We therefore
include a local open-weight model to show where the method stops helping. The
RQ1 model set mixes cost-efficient and larger models from different
providers, so differences between providers may partly reflect model size;
the planned tier comparison addresses this.

\textbf{Novelty.} The field is moving quickly, and several 2026 preprints on
LLM-guided risk analysis and agent test generation were available only as
titles during our literature search. Our novelty claim is limited to the
combination of pre-implementation slot binding with slot-mutation oracle
validation, slot-scoped repair and an executable regression ledger, to the
best of our knowledge as of October 2026.

\section{Conclusion and Future Work}

Current LLMs know how to write secure code but often fail to place the
defense where it belongs, static checkers overstate how often they succeed,
business-logic flaws are invisible to pattern-based tools, and defenses erode
as code evolves. This paper has argued that the enforcement location should
be treated as a first-class object. \sys{} compiles CWE knowledge and
developer-confirmed business rules into obligations, binds each obligation to
a named slot before implementation, trusts a security oracle only when it
fails on a weakened version of its own slot, confines repair to the failing
slot, and keeps validated oracles as a ledger that later features must
satisfy. The result for a developer is a short list of what was proven, what
failed, and what still needs human judgement, rather than an unverified body
of generated code. We have defined measurable notions of secure and
production-ready code, an evaluation against strong agentic, specification
and repair baselines, and an updated measurement of current models against
the base study.

Several directions follow. First, the framework produces training data that
prior secure-code training methods lack: slot repairs labelled by executable,
validated oracles. Reviewed training methods derive their security signal
from static analyzers or teacher models \cite{srcode2026,secvec2026}; using
oracle-labelled repairs for supervised and preference fine-tuning of a small
open model is a natural second phase. Second, richer mutation operators would
strengthen what a passing oracle certifies. Third, expressing the access
matrix in an established policy language would let the same profile drive
both application oracles and policy verification \cite{autocedar2026}.
Fourth, the ledger can run as a hook inside coding agents, which would allow
a study of defense survival in real multi-turn agent sessions. Finally, a
controlled study with developers would test whether the evidence report
reduces review time, not only the number of items to inspect.
